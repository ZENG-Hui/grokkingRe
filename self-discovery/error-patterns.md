# 错误模式清单

*从实际错误中提取，不是泛泛的原则。每条都有具体场景。*

## 1. 猜测代替证据
**场景：** `/opencode` 超时，我猜是 SSE 模式、serve 模式，连续提出两个假说都错了。
**实际原因：** `stdin=subprocess.DEVNULL` 缺失。
**正确做法：** 先做对比实验（`/run` 能跑通 vs `/opencode` 超时），用差异缩小范围，再下结论。
**信号：** 当我发现自己在说"可能是..."的时候，停下来，先设计一个能证伪的测试。

## 2. 消息又长又密
**场景：** 给 Hui 发调试分析，把分析过程、三个猜测、四条建议、一个问题全塞进一条消息。
**后果：** Hui 需要从中筛选关键信息再转达给 HG agent，浪费他的时间。
**正确做法：** 结论先行，一句话说清楚核心问题。细节和建议分层，让人可以选择性展开。

## 3. 不确认能力边界就设计方案
**场景：** 一开始花时间尝试 SSH 直连开发机，生成了 SSH key，写了配置，全部白费——因为网络根本不通。
**正确做法：** 先问"这条路在物理上走不走得通？"再投入时间设计。先验证约束，再构建方案。

## 4. 盲读大文件
**场景：** 还没发生严重的（今天 Hui 提醒了），但在读 AGENT_GUIDE.md（449行）和 SECURITY_POLICY.md（191行）时确实是全量读取。
**正确做法：** 先 `/wc` 或 `/ls -l` 看大小。超过 200 行的文件考虑分页或先看结构。给 opencode 派活时也要提醒。

## 5. 混用 message 工具和 reply text
**场景：** 早期犯过，导致 Feishu 上消息顺序混乱。
**规则：** 一次回复要么用 message 发，要么用 reply text，绝不混用。用 message 后回复 NO_REPLY。
